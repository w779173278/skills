# 技术文档编写规范专家 (Documentation Standards Skill)

本 Skill 指导 AI 助手或研发团队按照业界最佳的文档管理规范（参考大型微服务及分布式系统的模块化分层实践）来撰写、组织和重构软件仓库的技术文档。

## 1. 核心设计原则：中文模块化目录结构 ("1 + 1 + 5" 目录架构)

凡大型业务改造或核心模块的技术文档，禁止使用单个巨大的单体文档。必须采用分层目录，以中文重新进行物理命名，并在根目录下包含全局导航文件和基本概念文件：

```text
docs/[模块名称]/
├── 00_文档导航总览.md              # 【总索引】(总入口，串联时序与地图大图)
├── 01_基本概念与术语.md            # 【基本概念】(名词解释与一句话定义对照表)
├── 快速开始/                        # 【快速开始目录】(新手引导、本地快速运行与体验)
│   ├── 01_快速接入.md              # 最小化依赖配置与 Demo 运行
│   └── 02_调试与验证.md            # 本地调试、跑通单测与日志验证
├── 领域模型/                        # 【领域模型目录】(一等公民概念与实体关系图)
│   ├── 01_领域模型概述.md          # 整体实体关系 ER 图与限界上下文分层
│   └── 02_[概念实体名称].md        # 独立实体的通用领域模型四步定义
├── 功能行为/                        # 【核心功能行为目录】(匹配、状态机与核心策略)
│   ├── 01_[功能点行为定义].md      # 核心业务逻辑策略（如：并发控制/流量调度行为）
│   └── 02_[异常与重试策略].md      # 异常拦截、重试退避机制与死信处理
├── 开发与运维/                      # 【开发与运维目录】(实现设计、监控可观测与部署)
│   ├── 01_[快照缓存与重建机制].md  # 线程锁、并发缓存与失效设计
│   ├── 02_可观测性与监控规格.md     # 核心 Metrics 指标、告警红线与 Dashboard 配置
│   └── 03_部署与配置手册.md        # 配置参数约束与建议、部署模式
└── 参考规格/                        # 【参考规格目录】(DDL、API契约与数据字典)
    ├── 01_核心数据库表结构与DDL.md  # 建表 DDL、索引与表变化对照
    └── 02_API契约与错误码.md       # HTTP/gRPC API 定义及标准错误码
```

## 3. Diátaxis 写作框架标准

所有技术文档的定位必须划分入 [Diátaxis 框架](https://diataxis.fr/) 的四个独立象限，避免功能性步骤、技术细节与设计取舍混杂：

*   **教程 (Tutorials)**：学习导向，手把手带新手完成首次实践（如快速开始）。
*   **操作指南 (How-to Guides)**：问题导向，解决一个具体业务场景的配置步骤（如异常与重试策略配置）。
*   **参考规格 (Reference)**：信息导向，提供字典式技术参考（如 DDL 表结构、API 协议）。
*   **架构解释 (Explanation)**：理论导向，解释“为什么这样设计”、取舍考量与隔离安全（如领域模型实体定义、基本概念）。

## 4. 排版与链接规范

### 4.1 相对路径与代码符号链接
*   **文档间跳转**：必须使用 `./` 或 `../` 开头的相对路径跳转。例如：`[表结构 DDL](../参考规格/01_核心数据库表结构与DDL.md)`。禁止使用绝对路径（如 `file:///...`）或裸路径。
*   **代码文件与符号引用**：在技术文档中提到具体的文件或类名、方法名时，推荐使用带行号的相对路径或代码仓内相对路径链接（支持 IDE 跳转）。
    *   例如：`[TenantServiceImpl.java](../../src/main/java/com/example/service/impl/TenantServiceImpl.java#L45-L60)`

### 4.2 GitHub 级警示框 (Alerts)
合理使用警示框强调关键安全与设计红线。警示框不得连续摆放或嵌套：
*   `> [!NOTE]`：背景说明或补充细节。
*   `> [!TIP]`：最佳实践或性能小提议。
*   `> [!IMPORTANT]`：必须遵守的设计红线与必要前置。
*   `> [!WARNING]`：兼容性与配置冲突。
*   `> [!CAUTION]`：高危物理操作。

### 4.3 渲染与图表 (Mermaid & Tables)
*   时序与 ER 关系必须使用 `mermaid` 块呈现，保证版本管理。
*   变化对比、参数规格必须采用 Markdown 表格形式排列。

## 5. AI 助手执行工作流与自检清单

当 AI 助手被唤醒并要求编写、优化或重构技术文档时，必须遵循以下执行标准：

### 5.1 开启任务工作流
1. **澄清需求 (Clarify)**：确认文档类型 (Diátaxis)、受众目标与排查范围。
2. **结构设计 (Outline)**：设计并向用户提交待输出文档的大纲结构（采用 "1+1+5" 架构），等待用户确认。
3. **内容编写 (Drafting)**：通过 `view_file` 工具读取 `resources/templates/` 下对应的模板文件，并严格根据模板结构填充真实项目内容进行编写。
4. **自检修正 (Verify)**：根据 5.2 自检清单对内容进行最后润色，然后输出给用户。

### 5.2 AI 助手自检清单 (Pre-flight Checklist)
*   [ ] **路径合规性**：是否所有超链接都使用了以 `./` 或 `../` 开头的相对路径？
*   [ ] **目录架构**：是否已创建 `00_文档导航总览.md` 与 `01_基本概念与术语.md`，做到概念与领域模型设计明确拆分？
*   [ ] **模板调用方式**：是否通过 `view_file` 读取了 `resources/templates/` 目录下的对应模板，并与模板结构保持一致？
*   [ ] **信息清晰度**：操作性步骤 (How-to) 是否与字典信息 (Reference) 或设计选择 (Explanation) 混淆在一页？
*   [ ] **代码/表结构准确性**：DDL 与类名是否提供带行号的代码仓相对路径链接？
*   [ ] **排版格式**：警示框是否嵌套？排版是否存在拼写错误？
